# TypeScript

## Baseline

Follow the
[Google TypeScript Style Guide](https://google.github.io/styleguide/tsguide.html).
The following sections extend it and take precedence where they differ.

The guide is written for Google's own codebase. Its rules for the following
tools, which only Google uses, don't apply:

- The `@nocollapse` annotation, which the Closure Compiler reads
- The import rule for protocol buffer code generated by Apps JSPB, Google's
  internal protocol buffer library
- The tsetse and tsec conformance checks

Follow every other rule unless one of the following sections replaces it.

## Formatting

Oxfmt wraps code and JSDoc comments at 80 characters. It doesn't rewrap line
comments, so wrap them at 80 characters yourself. When Oxfmt joins a JSDoc
comment onto one line, the line can be up to 4 characters longer than 80. Leave
it as Oxfmt writes it.

## File Layout

Name files in `kebab-case`, such as `sensor-monitor.ts`, instead of the
`snake_case` that the guide uses.

Start every file with a JSDoc comment that has an `@file` tag and describes the
file. After the imports, order a file as follows:

1. Constants
2. Interfaces, types, and errors
3. Exported functions and classes
4. Functions and classes that aren't exported

Define base classes and values used as defaults before the code that uses them,
even when this changes the order. When a file becomes hard to follow in this
order, split it into smaller files.

## Naming

Write each acronym, initialism, or abbreviation in uniform case, as the "Naming"
section of [Coding Standards](../SKILL.md) describes, such as `sensorID` and
`parseCSVLine`. This replaces the guide's rule to treat them as words, as in
`sensorId` and `parseCsvLine`. No lint rule checks this, so check each name
yourself.

## Comments and Documentation

Write JSDoc comments as the guide describes, with these changes:

- Use the tag names that Oxfmt writes, such as `@returns` and `@file`, instead
  of the guide's `@return` and `@fileoverview`.
- Write an `@throws` tag for every error that a function throws itself, with the
  error's name in braces, such as `@throws {RangeError}`, followed by the
  condition that throws it.

## Types

- Annotate the return type of every function and method, exported or not. Write
  `: void` for a function that returns nothing.
- Let TypeScript infer the types of local variables, unless it can't infer them,
  such as for an empty array or a variable that starts as `undefined`.
- Type each parameter that the function doesn't change as read-only, so that
  callers can pass what they have:
  - `Iterable<Reading>` when the function loops over the argument once
  - `readonly Reading[]` when it needs `length` or indexing
  - `ReadonlyMap<string, number>` when it only reads a map
- Annotate each return value with a plain type, such as `Reading[]` or
  `Map<string, number>`, so that callers can use everything the type offers.
- Use `undefined` for a missing value, as `Map.get` and optional properties do.
  Use `null` only where an outside API uses it, such as JSON or the DOM.

## Function Signatures

- Make the main data inputs, usually one or two, positional. Put every option,
  meaning a parameter that changes how the function works rather than what it
  works on, in one options object that the function destructures, as in
  `hasGap(readings, {maximumGapSeconds = 300}: GapOptions = {})`. Callers then
  name each option, as in `hasGap(readings, {maximumGapSeconds: 600})`.
- Always put Boolean options in the options object.
- When a function must match a signature defined elsewhere, such as a callback
  that a library calls with positional arguments, follow that signature instead.

## Records and Classes

- Define a record of values as an interface whose properties are all `readonly`.
  `readonly` stops a property from being reassigned, but not an array or object
  stored in it from changing, so don't change those either.
- Use `private` instead of `#private` fields, as the guide asks, even though its
  reason, the cost of compiling for JavaScript older than ES2015, no longer
  applies.
- Use parameter properties, such as
  `constructor(private readonly configuration: MonitorConfiguration)`, as the
  guide asks, unless the project runs TypeScript files with Node directly. Node
  can't run parameter properties, so such a project sets `erasableSyntaxOnly` in
  the `tsconfig.json` file, which also rules out `enum`, and assigns fields in
  the constructor instead.

## Errors

When you throw an error while handling another, pass the caught error as the
cause, such as `throw new ConfigurationError(message, {cause: error})`.

### Messages

Write error, warning, and log messages in the style of the JavaScript runtime's
built-in messages:

- Start with a capital letter, unless the message starts with an identifier,
  which keeps its case. Don't end with a period.
- Put identifiers in backticks: parameter, variable, property, function, class,
  and type names, and names from outside the code that the code uses by their
  exact spelling, such as a CSV column. The runtime puts names in single quotes,
  but Node also prints string values in single quotes, so backticks keep names
  distinct from values. Escape each backtick inside a template literal.
- Show string values with `JSON.stringify`, so that they appear in double quotes
  and numbers appear bare. Write allowed values in double quotes too.
- Say what was expected, then the value received.
- When parsing input, put the location first, followed by a colon.

For example:

```ts
throw new RangeError(
  `\`method\` must be "lm" or "trf", got ${JSON.stringify(method)}`,
);

throw new ReadingFormatError(
  `Line ${lineNumber}: invalid \`measured_at\` value ` + JSON.stringify(text),
);
```

## Tests

- Use the project's test runner. In a new project, use Vitest.
- Put the tests of each file in a `*.test.ts` file next to it.
- Group the tests of each function or class in a `describe` block named for it.
  Name each test so that it completes a sentence that starts with that name,
  such as `test('averages only the most recent readings', ...)` inside
  `describe('TemperatureMonitor', ...)`.
- Tests need no JSDoc.

## Tooling

Format TypeScript with Oxfmt, lint it with Oxlint, and check types with
TypeScript. For projects without their own configuration, use
`assets/.oxfmtrc.json`, `assets/.oxlintrc.json`, and `assets/tsconfig.json` from
this skill.

The `tsconfig.json` file sets only type-checking options. When you copy it into
a project, add the options for the kind of project:

- For a Node package, set `module` to `nodenext`, and write relative imports
  with a `.js` extension, such as `'./sensor-monitor.js'`.
- For an app built with a bundler, such as Vite, set `module` to `preserve`.
- For code that Node runs directly, also set `erasableSyntaxOnly`.

In a new project, add `typescript`, `oxfmt`, `oxlint`, `oxlint-tsgolint`, and
`vitest` as development dependencies at exact versions, because Oxfmt hasn't
reached version 1.0 and its output can change between releases. For each file
you change, follow these steps:

1. Run `oxlint --type-aware --fix <file-path>`.
2. Fix the remaining findings by hand.
3. Run `oxfmt <file-path>`.

Then run `tsc` for the whole project, because it can't check one file with the
project's `tsconfig.json`, and run `vitest run <file-path>` for each test file
that covers the code you changed.

When the configuration isn't in the project, pass `-c <configuration-path>` to
Oxlint and Oxfmt with the path to `assets/.oxlintrc.json` or
`assets/.oxfmtrc.json`. For a file outside any project, pass the type-checking
options to `tsc` as flags instead:

```sh
tsc --noEmit --noUncheckedIndexedAccess --exactOptionalPropertyTypes FILE-PATH
```

Replace `FILE-PATH` with the path to the TypeScript file.

Suppress an Oxlint finding with a comment that names the rule and gives the
reason, such as:

```ts
// oxlint-disable-next-line typescript/no-non-null-assertion -- Filled above.
```
